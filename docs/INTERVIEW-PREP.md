## 第1条：多智能体编排（Coordinator + 4 Agent + Checkpoint）

### 📚 面试官想考的知识点

| 知识点 | 深度要求 |
|--------|----------|
| 为什么用多智能体而不是单 Agent | 职责分离、可扩展性 |
| Coordinator 怎么路由 | 条件路由 / LLM 意图识别 |
| Agent 间怎么通信 | State 共享（不直接耦合）|
| Checkpoint 是什么 | 节点级状态持久化 |
| 断点恢复解决什么问题 | 中断续跑、省 token |

### ❓ 高频问题 & 回答要点

**Q1: 为什么用多智能体架构？单 Agent 不行吗？**
```
答: 职责分离——知识检索、经验管理、面试分析、文档生成是不同领域，
单 Agent 混在一起会让 system prompt 臃肿、工具集混乱。
多智能体让每个 Agent 专注一件事（单一职责），
Coordinator 负责任务分发，扩展新能力只需加节点。
面试加分: 提到"可控性"——每个 Agent 可单独测试（我的节点评测36/36）
```

**Q2: Coordinator 怎么决定路由到哪个 Agent？**
```
答: 两种方式结合：
① LLM 意图识别（结构化输出 IntentOutput，含 confidence）
② 低置信度兜底（confidence<0.4 → 走 chat，不硬分类）
面试加分: 我评测过 25 个意图用例准确率 96%，
并优化过提示词边界（"查看README"vs"查知识库"的区分）
```

**Q3: 多个 Agent 之间怎么协作？会重复做事吗？**
```
答: 通过统一的 AgentState 共享上下文——
Coordinator 写入 intent，下游 Agent 读取，避免直接互相调用。
每个 Agent 职责边界清晰（knowledge 不写经验、experience 不查知识库），
靠"职责隔离"避免重复。
面试加分: 我做了 State 传递测试验证 message/project_id 贯穿全链路
```

**Q4: Checkpoint 断点恢复是什么？怎么实现的？**
```
答: LangGraph 的 MemorySaver，每个节点执行后保存 State 快照，
用 thread_id 管理会话。中断后同 thread 恢复，从保存点继续，
不重跑已完成节点（省 token、保状态）。
面试加分: 我评测发现"Session 不可序列化导致 checkpoint 失败"，
改成 managed value 注入后，同 thread 第二次 10.9s→0.0s
```

**Q5: State 里放什么？怎么避免序列化问题？**
```
答: State 放可序列化的业务数据（message/intent/response）。
连接资源（db session）用 managed value 按需注入，不参与持久化。
面试加分: 这是我在评测中踩过的真实坑（缺陷6），
体现对 LangGraph 底层序列化机制的理解
```

## 第2条：上下文与长期记忆（三层上下文 + 跨会话召回）

### 📚 知识点

| 知识点 | 深度 |
|--------|------|
| 三层上下文是什么 | 聊天历史/对话摘要/项目记忆 |
| 短期记忆 | 最近N条消息（token预算内）|
| 中期记忆 | 旧对话压缩成摘要 |
| 长期记忆 | 项目级决策/偏好（LLM提取沉淀）|
| 跨会话召回 | 新会话注入历史记忆 |

### ❓ 高频问题 & 回答要点

**Q1: 三层上下文分别是什么？各解决什么问题？**
```
答: 
① 聊天历史（短期）: 当前对话连贯性
② 对话摘要（中期）: 旧对话不丢关键信息（压缩代替丢弃）
③ 项目记忆（长期）: 跨会话核心知识（决策/偏好）
面试加分: 核心思想是"窗口满了先压缩而不是丢弃"
```

**Q2: 长期记忆怎么提取和沉淀？**
```
答: LLM 从对话中提取结构化记忆（MemoriesExtractOutput schema），
分类型（decision/progress/problem/preference），带重要度1-5，
写入 project_memories 表；有去重机制。
面试加分: 我评测过"沉淀5条决策 → 新会话问数据库选型 → 正确召回PostgreSQL"
```

**Q3: 记忆召回时怎么保证注入质量？**
```
答: 按重要度降序取高价值记忆 + 最近摘要注入 system prompt。
（进阶: 可加时效衰减——重要度×新鲜度，近期记忆优先）
```

**Q4: 上下文 token 超了怎么办？（重点）**
```
答: Token 预算制三级降级：
① 先带最近消息（保证连贯）
② 预算超 → 旧消息压缩成摘要
③ 还不够 → 丢最旧（关键信息已在摘要）
面试加分: 我测过历史窗口5/10/15条的 prompt token（112→206），
明确"上下文完整 vs token 成本"的权衡
```

## 第3条：Tool Calling & MCP

### 📚 知识点

| 知识点 | 深度 |
|--------|------|
| 什么是 Tool Calling | Agent 调用外部函数 |
| 怎么决定调哪个工具 | LLM 结构化判断 |
| 参数怎么保证正确 | Pydantic Schema 约束 |
| MCP 是什么 | 标准协议连接外部工具 |
| MCP 架构 | Client(Agent) ↔ Server(工具) |

### ❓ 高频问题 & 回答要点

**Q1: Tool Calling 是怎么实现的？**
```
答: 用 Pydantic Schema（ToolCallOutput）约束 LLM 输出
{use_tool, tool, arguments}，LLM 判断是否调用+给参数，
代码反序列化后执行，再基于结果回答。
面试加分: 对比过"文本解析参数"（T13）vs"结构化输出"（T14）——
后者解决了 type 字段丢失问题，参数完整率100%
```

**Q2: 参数错了或缺失怎么办？**
```
答: 三层防护：
① Schema 校验（LLM 输出必须符合格式）
② 兜底（如 save_document 的 content 为空时先用 LLM 生成）
③ 执行失败降级（返回错误信息，不崩溃）
面试加分: 我评测发现"Document 保存空内容"缺陷并修复
（content 0→3844字符）
```

**Q3: MCP 是什么？怎么接入的？**
```
答: Model Context Protocol，AI 应用调用外部工具的开放标准。
我的实现: Agent 作为 MCP Client，通过 stdio 启动 mcp_server.py 子进程，
JSON-RPC 通信，调用 GitHub 查询/Web 搜索/文件读取。
面试加分: 我独立测试过 MCP 成功率 10/10（平均0.82s），
并处理了"事件循环内不能 asyncio.run"等坑
```

**Q4: 为什么用 MCP 而不是直接写函数？**
```
答: 标准化——MCP 工具是独立服务，任何 MCP 客户端都能复用，
Agent 只需按协议调用，生态里现成的工具服务器可直接接入。
```

## 第4条：稳定性与缓存（参数校验 + 兜底 + Redis Cache）

### 📚 知识点

| 知识点 | 深度 |
|--------|------|
| 低置信度兜底 | 意图不确定时走默认 |
| Redis 缓存 | 相同请求直接返回 |
| 缓存 key 设计 | 稳定输入才可命中 |
| 缓存降级 | Redis 挂了不影响主流程 |

### ❓ 高频问题 & 回答要点

**Q1: 低置信度兜底是什么？为什么需要？**
```
答: LLM 意图识别输出 confidence，<0.4 时不硬分类，兜底走 chat。
原因: 小模型对模糊输入会"瞎猜"，兜底避免错误路由。
面试加分: 边界用例（空输入/符号/乱码）100% 正确兜底
```

**Q2: Redis 缓存怎么做的？收益如何？**
```
答: LLM 响应缓存——相同请求命中直接返回。
key 基于 system_prompt + 用户消息（稳定输入）。
收益: 意图识别 5.4s→0.00s，chat_completion 7.9s→0.00s。
面试加分: 我踩过坑——key 含聊天历史导致永不命中（缺陷4），
修复为只基于稳定输入，这是缓存设计的经典陷阱
```

**Q3: Redis 挂了怎么办？**
```
答: 所有 Redis 操作 try-except 降级——失败时直接调 LLM，
不影响主流程（用可靠性换可用性）。
```

**Q4: 缓存正确性怎么保证？**
```
答: 评测验证: 命中/未命中回答一致、
不同 system_prompt 不误命中、缓存 TTL 过期后重新生成。
```

## 第5条：Agent 评测体系

### 📚 知识点

| 知识点 | 深度 |
|--------|------|
| 三层测试 | 节点/链路/性能 |
| 为什么节点测试 | 快速定位单个 Agent 问题 |
| Trace 记录什么 | 每步耗时/token/状态 |
| 评测发现问题 | 测试驱动优化 |

### ❓ 高频问题 & 回答要点

**Q1: 你的评测体系怎么设计的？**
```
答: 三层：
① 节点测试: 36用例单节点直测（快速、覆盖全）
② 链路测试: 5关键场景全链路（验证编排）
③ 性能测试: 并发压测 + 延迟拆分
所有测试记录 Trace（coordinator→agent→tool 每步耗时/token/状态）
```

**Q2: 为什么记录 Trace 而不是只看结果？**
```
答: 只看最终结果无法定位问题出在哪一步。
Trace 能看到"哪个节点选的工具错""哪步耗时最长""token 花在哪"，
评测变成数据驱动的。
```

**Q3: 评测发现了什么真实问题？（重要，展示价值）**
```
答: 6个缺陷，举例：
① Redis 缓存 key 含历史 → 永不命中（性能测试发现）
② AgentState 含 Session → checkpoint 失败（断点测试发现）
③ Document 工具参数缺失 → 空内容（链路测试发现）
每个都是"测试定位 → 根因分析 → 修复 → 复测"闭环
```

**Q4: 延迟拆分怎么看瓶颈？**
```
答: 完整请求的 Trace 拆成 coordinator/agent/tool 各段耗时，
占比最高的就是瓶颈（如 tool 调用占77%时优先优化工具）。
```

## 附加：高频综合问题

**Q1: 这个项目你最大的收获是什么？**
```
答: 三层：
① 多智能体不是堆 Agent，而是靠 State 共享和职责边界协作
② 可观测性优先——先让系统能被 Trace，才能数据驱动优化
③ 测试的价值——评测发现6个真实缺陷，比"感觉能用"可靠
```

**Q2: 如果重新做，哪里会改进？**
```
答: 三点：
① 对话摘要更主动（达到N条自动生成，不只随记忆沉淀）
② 记忆召回加时效衰减（重要度×新鲜度）
③ 并发更大规模压测（当前5并发受LLM耗时限制）
```

**Q3: 小模型（Ollama）和大模型（Qwen API）你怎么取舍？**
```
答: 开发用小模型（免费快），生产用API（效果稳）。
结构化任务用低温度保稳定，创意任务用高温度发散。
```
